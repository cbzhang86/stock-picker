## 备份「日期与 mtime 不符」追查（20:40-21:00）——结论：不是 bug，是复制方式差异

**结论先行**：文件名日期没错（就是 09-14 备份的），是**两种复制方式的时间戳语义不同**导致 mtime 误导了判断。

- 实测（Temp\mtime_probe，源文件 mtime 设为 2026-01-02）：
  - bash `cp`（不带 -p）→ 目标 mtime = **复制时刻**
  - `cp -p` / `Copy-Item` / .NET `File.Copy` / python `shutil.copy2` → **保留源文件 mtime**
- 证据链：
  - `predictions_20260913.db`、`v1_20260913.json`：mtime 09-13 20:03 = **周检运行时刻**（automation_runs：09-13 20:00:33 启动）→ 不带 -p 的 `cp`
  - `predictions_20260914.db`（mtime 09-12 20:09 = 源库 mtime）、`v1_20260914.json`（mtime 09-05 12:14 = 源 v1.json mtime）→ `shutil.copy2`
  - 来源实锤：会话 `64e94934`（09-14 10:57:52，model=hy3；因 09-13 周检推送未真正送达而手工重跑周检）先跑 `cp`（未生效）再 `shutil.copy2`，命令原文在该会话 jsonl 第 101/105 行
- **重要副产品**：三份 predictions 备份 md5 全同（c660b5ae3b31）且与当前源库一致 → 自 09-12 20:09 起 DB 零写入，与 09-08~09-11 连续 4 个交易日无选股产出（周检 A=1 告警）互相印证
- 排除干扰项：`outcomes.updated_at` 存的是 SQLite `CURRENT_TIMESTAMP`（UTC），12:09 UTC = 20:09 CST 是同一时刻，不是时区 bug
- 待决策改进：① 备份统一复制方式并落 manifest（备份时刻+md5+源 mtime），别再用 mtime 判新鲜度；② 周检提示词里的 `<YYYYMMDD>` 由 AI 现场计算有填错风险 → 改成命令内 `$(date +%Y%m%d)`
- 顺带确认：`send_wechat.py` 的"假成功"bug 已修（09-14 10:47，新增 ret 校验，`ret in (0,"0")` 才算成功）
